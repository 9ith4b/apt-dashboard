# 测试、验收与交付路线

## 1. 测试分层

### 单元测试

- URL、域名、IP、哈希、邮箱和时间规范化；
- Exact Hash、SimHash 和事件相似度特征；
- 相关性分数与原因输出；
- 日期桶选择和 `Asia/Shanghai` 区间转换；
- WatchRule JSON Schema 和匹配逻辑；
- Observable 提升条件与置信度规则。

### 集成测试

- PostgreSQL 约束、迁移和并发版本冲突；
- Redis/Celery 任务幂等、重试和死信隔离；
- MinIO 原始内容、正文版本和 Evidence 定位；
- RSS、网页、X、Telegram 连接器使用固定录制响应，不依赖真实外部服务；
- LLM 与富化 provider 使用契约假服务测试超时、无效 JSON、429 和部分响应。

### API 契约测试

- OpenAPI 可生成 TypeScript 类型且无未声明响应；
- 登录、CSRF、分页、筛选、错误结构和幂等键；
- `PATCH` 版本冲突返回 409；
- 事件合并和撤销不会丢失 Report 或 Evidence；
- 未配置外部凭据时返回可操作状态而不是 500。

### 前端测试

- 关键组件的加载、空、失败、候选和确认状态；
- 日期范围写入 URL 并在刷新后恢复；
- 证据点击定位正确片段；
- 审核草稿、字段决策、完成校验和冲突处理；
- 键盘导航、焦点管理、对比度和减少动画设置。

### 端到端测试

1. 创建 RSS 数据源并通过连接测试。
2. 同步包含 Lazarus 虚假面试内容的测试 feed。
3. 生成 IOC、Actor、能力和受害目标候选。
4. 第二篇报道进入后形成事件合并审核任务。
5. 用户完成字段审核并确认一个 Threat Event。
6. 有证据的域名从 Observable 提升为 Indicator。
7. Lazarus 持续跟踪页出现一条事件、两篇报道。
8. 自定义日期和导出内容使用相同统计口径。

## 2. 必测业务场景

| 场景 | 期望结果 |
| --- | --- |
| 同一正文来自不同 URL | 保留来源，标记精确重复，不重复分析 |
| 两篇文章描述同一攻击 | 两条 Report，一条确认事件 |
| 同名但不同组织 | 不自动合并，进入实体审核 |
| 仅出现普通 IP | 创建 Observable，不创建 Indicator |
| 只有相似 TTP | 不自动确认 Actor 归因 |
| 模型超时 | 规则结果可用，任务可重试 |
| 模型返回不存在的证据 ID | 整个语义结果拒绝写入领域对象 |
| X 凭据失效 | X 源标记失败，RSS 等来源继续运行 |
| 日期区间 31 天 | 按日聚合 |
| 日期区间 32 天 | 按周聚合 |
| 日期区间 181 天 | 按月聚合 |
| 事件撤销确认 | 画像和跟踪统计失效并重新计算 |

## 3. 性能与容量测试

初始基准数据：10 万篇 Report、2 万个 Threat Event、100 万个 Observable/关系记录。

- 情报流查询 P95 小于 800 ms；
- 事件详情 P95 小于 1.5 s；
- 365 天跟踪聚合冷查询小于 3 s，缓存查询小于 500 ms；
- 单 Worker 每小时可处理不少于 300 篇普通文章，外部限速时间不计入；
- 任务队列积压后恢复期间，API 查询性能不显著退化。

## 4. 安全测试

- SSRF：IPv4/IPv6 私网、DNS 重绑定和跨重定向测试；
- XSS：标题、正文、来源名、模型输出和导出内容；
- 提示注入：正文包含伪系统指令时不得改变输出 Schema 或执行工具；
- 会话：固定会话、CSRF、暴力登录、Cookie 属性；
- Secret：日志、错误响应、数据库、浏览器网络响应和前端构建产物扫描；
- 依赖与镜像漏洞扫描。

## 5. 视觉验收

- 以 v3 高保真原型为基准，覆盖 1440×900 和 1024×768。
- 允许字体抗锯齿等非结构差异；导航、内容层级、状态色、间距和关键组件不得漂移。
- 每个页面至少包含默认、加载、空、失败和有数据状态截图。
- 持续跟踪页额外覆盖月、年、自定义日期 Popover 和长区间聚合状态。

## 6. 开发里程碑

### M0：工程基座

- Monorepo、开发容器、认证、数据库迁移、对象存储、任务队列、OpenAPI 类型生成和 CI。

### M1：采集闭环

- RSS/网页连接器、数据源管理、原始归档、正文抽取、报道去重和情报流。

### M2：分析与审核

- IOC/实体提取、可插拔 LLM、Evidence、事件候选、钻石模型和审核队列。

### M3：情报工作台

- Actor 画像、Campaign 时间线、IOC 狩猎、富化和 Indicator 提升。

### M4：持续跟踪

- X/Telegram 连接器、关注规则、日期聚合、变化检测、摘要和导出。

### M5：加固与发布

- 性能、安全、备份恢复、可访问性、视觉回归、部署与运维验收。

每个里程碑必须通过对应自动化测试和产品验收后才能进入下一阶段。

## 7. MVP 发布门槛

- 无 P0/P1 已知缺陷；
- 所有数据库迁移可在生产副本上成功演练；
- 关键 E2E 场景连续运行三次通过；
- 原始内容到 Evidence 的追溯完整率为 100%；
- 已确认归因均有直接 Evidence 或明确的分析员判断记录；
- 备份恢复、密钥轮换和应用回滚完成演练；
- 数据源失败不会导致 API 或其他采集源不可用；
- 高保真原型中的 10 个核心页面均通过视觉和交互验收。

## 8. 工程启动清单

- 冻结 v3 原型和设计令牌；
- 建立 ADR 模板并记录首批架构决策；
- 创建前后端工程、Compose、CI 和环境示例；
- 先定义 OpenAPI 与数据库迁移，再实现页面数据访问；
- 建立无版权风险的脱敏测试语料和连接器夹具；
- 配置代码检查、类型检查、测试覆盖率和依赖扫描门禁；
- 为每个里程碑建立可演示的纵向切片，不先孤立开发全部页面。
